# 04. Сервер

## 4.1. Общие принципы

- Сервер — единственный источник истины для боя, рейтинга и экономики.
- `sim-core` — чистая Kotlin-библиотека без Ktor, JDBC, корутин и системного времени.
- Матч исполняется на выделенном platform thread; I/O — через очереди и корутины вне тика.
- Все входные данные валидируются до попадания в симуляцию.
- Любая операция, меняющая валюту или рейтинг, идемпотентна.
- Конфигурация и контент проверяются при старте; при ошибке процесс не стартует.

### 4.2.1. Правила зависимостей

- `sim-core` не зависит ни от чего, кроме `shared-common` и стандартной библиотеки.
- `sim-runtime` зависит от `sim-core`, `sim-content`, `sim-replay`.
- `app` зависит от доменных модулей, но не наоборот.
- Доменные модули не импортируют классы Ktor.
- `shared-protocol` генерируется из схем; руками не правится.

## 4.3. Модуль app (Ktor)

### 4.3.1. Ответственности

- HTTP-роутинг, сериализация, аутентификация, авторизация.
- WebSocket-сессии, подписка на матчи, fanout.
- Валидация запросов на границе.
- Оркестрация доменных сценариев.
- Health/readiness, метрики, трейсы.

### 4.3.2. Плагины Ktor

- `ContentNegotiation` (kotlinx.serialization JSON).
- `Authentication` (JWT).
- `CORS` (только доверенные origin).
- `Compression` (gzip/brotli для REST, не для WS).
- `CallLogging` + MDC с `traceId`.
- `StatusPages` (единый формат ошибок).
- `RateLimit` (Redis-backed).
- `WebSockets`.

### 4.3.3. Формат ошибок

```json
{
  "error": {
    "code": "GENOME_BUDGET_EXCEEDED",
    "message": "Стоимость генома 3120 BM превышает лимит 3000 BM",
    "details": {"cost": 3120, "limit": 3000},
    "traceId": "01J..."
  }
}
```

Коды ошибок стабильны, тексты локализуются на клиенте по коду. HTTP-статусы:

| Статус | Когда |
|---|---|
| 400 | Невалидный запрос, схема, диапазон |
| 401 | Нет или истёк токен |
| 403 | Нет прав, заблокирован |
| 404 | Ресурс не найден или скрыт |
| 409 | Конфликт версии, повторная операция |
| 422 | Домен-валидация (геном, армия) |
| 429 | Лимит запросов |
| 500 | Внутренняя ошибка |
| 503 | Зависимость недоступна |

## 4.4. Модуль auth

### 4.4.1. Модель

- `users`: id, email, password_hash, status, created_at.
- `identities`: provider, subject, user_id (OAuth).
- `sessions`: refresh_token_hash, user_agent, ip_hash, expires_at, revoked_at.
- `email_tokens`: тип (verify/reset), хеш, срок.

### 4.4.2. Токены

- Access JWT: 15 минут, подпись EdDSA, claims `sub`, `sid`, `role`, `jti`.
- Refresh: 30 дней, хранится хешем, ротация при каждом использовании.
- Отзыв: по `sid` в Redis (denylist) и в БД.
- Пароль: Argon2id (memory 64 МБ, iterations 3, parallelism 4).

### 4.4.3. Защита

- Лимит попыток входа: 10 за 15 минут на IP+email.
- Проверка пароля по списку утечек (k-anonymity API) — Should.
- Письма подтверждения и сброса — одноразовые, срок 30 минут.
- Не раскрывать существование email в ответах.

## 4.5. Модуль lab

### 4.5.1. Валидация генома

Порядок:

1. Проверка схемы JSON (типы, обязательные поля, диапазоны).
2. Проверка ссылок на органы и их версии.
3. Проверка сокетов и геометрии.
4. Проверка обязательных органов (ядро, метаболизм).
5. Проверка бюджета, массы, энергии, контроля.
6. Проверка поведения (граф, сложность, ссылки).
7. Канонизация и хеш.
8. Расчёт производных характеристик и стоимости.

Ошибки делятся на:

- `ERROR` — сохранение невозможно;
- `WARNING` — сохранение возможно, но есть риск;
- `INFO` — подсказка.

### 4.5.2. Канонизация

- Ключи JSON сортируются.
- Числа приводятся к целым, где это предусмотрено схемой.
- Строки нормализуются (Unicode NFC, trim).
- Порядок органов сортируется по `socketId`.
- Хеш: BLAKE3 от канонического JSON + `catalogVersion` + `rulesetVersion`.

### 4.5.3. Версионирование

- `creature_versions` неизменяемы.
- Новая правка создаёт версию с `parent_version_id`.
- Удаление — мягкое, с запретом, если версия используется в активной армии или матче.

## 4.6. Модуль army

- Армия: имя, список `(creatureVersionId, count, placement)`.
- Ограничения: ≤ 40 существ, ≤ 6000 BM, уникальные позиции, зона развертывания.
- Валидация выполняется на сервере при сохранении и повторно при старте матча.
- Армия фиксируется в матче как снимок: `army_snapshot` (JSONB + хеш).
- Изменение армии во время матча невозможно.

## 4.7. Матчмейкинг

### 4.7.1. Очередь

- Redis Sorted Set по рейтингу, ключ `mm:queue:{region}:{mode}`.
- Элемент: `userId`, `armyId`, `rating`, `enqueuedAt`, `budget`.
- Подбор: ищем ближайший рейтинг в окне, проверяем бюджет и регион.
- Окно: ±100, растёт на 25 каждые 5 секунд до ±400.
- После 45 секунд — бот с рейтингом, близким к игроку.

### 4.7.2. Подтверждение

- Оба игрока получают `match_found` с `matchId` и `confirmDeadline` (10 с).
- При подтверждении армии фиксируются, создаётся `match` в статусе `ALLOCATING`.
- При отказе или таймауте — возврат в очередь, штраф отказнику.
- Штраф: 30 с, 2 мин, 10 мин, 30 мин; сброс через 24 часа без отказов.

### 4.7.3. Рейтинг

- Glicko-2, начальный рейтинг 1500, RD 350, volatility 0.06.
- Обновление после матча, асинхронно, но до показа результата.
- Отдельные рейтинги: `duel`, `siege`, `season`.
- Защита от фарма: минимальное количество матчей, анти-сговор.

## 4.8. Scheduler и sim-worker

### 4.8.1. Scheduler

- Лидер-лок в Redis (`SET NX PX`), 2 реплики.
- Получает заявку на матч, выбирает worker по:
  - свободным слотам;
  - региону;
  - версии контента;
  - текущей нагрузке.
- Резервирует слот через Redis (`worker:{id}:slots`).
- Передаёт `start_match` по внутреннему gRPC/HTTP.
- При неудаче — retry с другим worker, затем отмена и возврат рейтинга.

### 4.8.2. Worker

- Держит пул потоков, по одному на матч.
- Публикует heartbeat каждые 5 секунд.
- При потере heartbeat scheduler помечает слоты свободными, матчи аннулируются.
- Graceful shutdown: перестаёт принимать новые матчи, ждёт завершения текущих до 2 минут.

### 4.8.3. Реестр матчей

- Redis Hash `match:{id}`: workerId, status, tick, startedAt, players, spectatorCount.
- TTL 2 часа после завершения.
- Gateway читает реестр для маршрутизации зрителей и реконнекта.

## 4.9. Tick loop

### 4.9.1. Псевдокод

```kotlin
class MatchActor(
    private val state: MatchState,
    private val rules: Ruleset,
    private val out: MatchOutput
) {
    fun run() {
        val tickNanos = 1_000_000_000L / rules.tickRate
        var next = System.nanoTime()
        while (state.status == RUNNING) {
            val now = System.nanoTime()
            if (now < next) LockSupport.parkNanos(next - now)
            val started = System.nanoTime()

            state.step()                 // чистая детерминированная логика
            if (state.tick % rules.snapshotEveryTicks == 0) {
                out.snapshot(state.buildSnapshot())
            }
            if (state.tick % rules.keyframeEveryTicks == 0) {
                out.keyframe(state.buildKeyframe())
            }

            val spent = System.nanoTime() - started
            metrics.observeTick(spent)
            next += tickNanos
            if (System.nanoTime() - next > tickNanos * 3) {
                metrics.overrun()
                next = System.nanoTime()
            }
        }
        out.finish(state.result())
    }
}
```

### 4.9.2. Правила тика

- Симуляция не читает системное время.
- Все события тика применяются в конце тика в порядке `(phase, entityId, sequence)`.
- Снапшоты формируются из состояния на границе тика.
- При перегрузке пропускаются снапшоты, но не тики. Если тик не успевает 3 раза подряд — матч помечается `DEGRADED`, логируется.
- Один матч не может выполняться параллельно на нескольких потоках.

### 4.9.3. Фазы тика

| Фаза | Что происходит |
|---|---|
| 0. Input | Применение предбоевых данных (только тик 0) |
| 1. Sensors | Обновление восприятия, видимости, памяти |
| 2. AI | Принятие решений (каждые 3 тика на сущность) |
| 3. Intents | Преобразование решений в намерения движения/атаки |
| 4. Movement | Интеграция, коллизии, навигация |
| 5. Combat | Атаки, снаряды, попадания |
| 6. Effects | Статусы, урон, смерть, лечение |
| 7. Economy | Энергия, голод, ресурсы, размножение |
| 8. Objectives | Ульи, зоны, условия победы |
| 9. Events | Формирование событий для клиента |
| 10. Hash | Хеш состояния для проверки детерминизма |

## 4.10. Снапшоты и события

### 4.10.1. Снапшот

- Частота: 10 Гц (каждые 3 тика).
- Содержимое: тик, сущности, снаряды, ульи, ресурсы, счёт, флаги.
- Квантование: координаты в сантиметрах (`uint16`), углы `uint16`, HP `uint16`.
- Дельта: относительно последнего ключевого кадра (раз в 30 тиков).
- Хеш: `xxHash64` от состояния, для проверки.

### 4.10.2. События

- События отправляются отдельным списком в снапшоте.
- Типы: `spawn`, `death`, `attack`, `hit`, `heal`, `status`, `ability`, `objective`, `chat`, `match_end`.
- Каждое событие имеет `eventId`, `tick`, `entityId`, `type`, `payload`.
- Клиент не обязан показывать все события; сервер не полагается на клиент.

## 4.11. Реконнект

1. Клиент переподключается с `matchId` и токеном.
2. Gateway проверяет участие или право зрителя.
3. Клиент получает `match_resume` с последним ключевым кадром и текущим тиком.
4. Дальше идут обычные снапшоты.
5. Если матч завершён — клиент получает результат и ссылку на реплей.

Буфер ключевых кадров: последние 60 секунд (60 кадров) в памяти worker и Redis.

## 4.12. Конфигурация

- Формат: HOCON + переменные окружения.
- Валидация при старте через декларативную схему.
- Секреты только из Vault/K8s Secrets.
- Пример ключей:
  - `server.port`, `server.shutdownTimeout`;
  - `db.url`, `db.poolSize`;
  - `redis.url`;
  - `auth.jwt.issuer`, `auth.jwt.publicKey`;
  - `sim.tickRate`, `sim.snapshotEveryTicks`, `sim.maxEntities`;
  - `mm.ratingWindow`, `mm.botAfterSeconds`;
  - `features.duel`, `features.siege`.

## 4.13. Обработка ошибок и деградация

| Ситуация | Действие |
|---|---|
| Невалидный геном | 422, понятная ошибка, матч не стартует |
| Версия контента недоступна | 409, предложение обновить клиент |
| Очередь переполнена | 429 + оценка времени |
| Worker не отвечает | Переназначение или отмена, возврат рейтинга |
| Тик превышает бюджет | Метрика, деградация снапшотов, алерт |
| Ошибка записи результата | Retry с идемпотентным ключом, DLQ |
| Ошибка S3 | Реплей помечается, повторная попытка, матч не блокируется |

## 4.14. Безопасность сервера

- Все эндпоинты, кроме health и auth, требуют токен.
- Проверка владения ресурсом на каждом запросе.
- Ограничение размера тела запроса: 256 КБ для REST, 64 КБ для WS-сообщения.
- Ограничение частоты: 60 REST/мин на пользователя, 20 WS-команд/мин.
- Запрет произвольных URL и SSRf.
- SQL только через jOOQ с параметрами.
- Логи не содержат токенов, паролей, email в открытом виде.
- Админ-действия аудируются.

## 4.15. Производительность и масштабирование

### 4.15.1. Бюджет матча

| Ресурс | Бюджет |
|---|---|
| CPU на тик | 8 мс p95 |
| Память матча | 64 МБ |
| Снапшот | 6 КБ |
| Сеть на зрителя | 30 КБ/с |
| Потоки | 1 sim + 1 I/O |

### 4.15.2. Оценка мощности

- 80 существ × 30 тиков = 2 400 обновлений/с.
- AI: 80 × 10 = 800 решений/с.
- Целевая ёмкость: 10 матчей на ядро с запасом 2×.
- 8-ядерный узел: ~80 матчей, ~6 400 существ.
- 4 000 матчей: ~50 ядер симуляции + API.

### 4.15.3. Горизонтальное масштабирование

- App: stateless, sticky sessions для WS.
- Sim: scheduler распределяет матчи; worker не хранит состояние между матчами.
- Redis: pub/sub каналы по `matchId`.
- Postgres: партиционирование результатов по месяцам, read-реплики для статистики.
